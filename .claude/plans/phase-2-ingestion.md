## Goal
The `/api/ingest` (webhook) and `/api/email` (Mailgun) endpoints accept requests, verify their secrets (X-Make-Secret / HMAC-SHA256), validate the `truck_id` against active trucks, and store the raw incoming data in the `posts` table — all verifiable via curl against seeded dev trucks.

## Out of Scope
- The Swedish NLP parser (`src/lib/parser/*`) — normalize, negation, location, date, time, confidence. Phase 3.
- Geocoding (`src/lib/geocoding.ts` + Nominatim). Phase 3.
- Writing `locations` rows — no location insert, no `last_known_lat/lng` update, no override/priority logic, no time-window overlap detection. Phase 3.
- Graceful **caption+60s** deduplication logic — deferred to Phase 3 with the rest of the ingestion-service logic. (Note: `instagram_post_id` uniqueness is enforced at the DB level from Phase 2 via the `posts_instagram_post_id_unique` partial index — the service must catch the resulting Postgres unique-violation on duplicate insert; see Rationale.)

- `proxy.ts` secret/session enforcement and rate limiting (Upstash). Phase 7 — endpoints verify their own secrets inline for now.
- Supabase Realtime. Phase 4.
- Exercising/verifying RLS policy behaviour — the migration authors the full documented policies, but they are **not exercised** in Phase 2 (all writes use `supabaseAdmin`, which bypasses RLS). Anon-read policies first matter in Phase 4.
- Real Make.com scenarios and Mailgun domain/route configuration — **Phase 8**. This phase builds both endpoints and simulates each lane with hand-crafted curl payloads; no external accounts are set up.
- Hosted Supabase project + `supabase db push` to prod — Phase 5 (first deploy). This phase is **local only**.
- Automated tests beyond the two pure security functions — the ingestion **integration tests** (`tests/integration/ingestion.test.ts`, against local Supabase) and parser unit tests stay in Phase 3. Route handlers remain curl-verified. Only `verifyMailgunSignature` + `extractTruckIdFromRecipient` get Vitest unit tests now (security boundary, zero infra needed).

## Steps

1. **Install WSL2** — `wsl --install` in elevated PowerShell, reboot. Prerequisite for Docker Desktop's backend. Verify `wsl --status`.
2. **Install Docker Desktop** — install with the WSL2 backend, launch, confirm the engine is running. Verify `docker --version` and `docker ps`. Nothing local-Supabase runs without this.
3. **Install the Supabase CLI** — `npm i -D supabase` (devDependency, run as `npx supabase`; Supabase doesn't support global `npm -g`, and this pins the version in the repo). Verify `npx supabase --version`.
4. **`npx supabase init` + write `0001_initial_schema.sql`** — generates `config.toml`; author the schema. Nothing can be stored or validated against a truck until the tables, indexes, and RLS exist.
5. **Write `seed.sql`, then `npx supabase start`** (first boot auto-applies migrations + seed; use `npx supabase db reset` only to re-apply after later schema/seed edits) — bring the local stack up. Curl testing needs real `truck_id`s (active + one inactive to test rejection). Copy the values printed by `supabase start` into `.env.local`: **`NEXT_PUBLIC_SUPABASE_URL` (the API URL), the anon key, and the service-role key.** Also set **dev-invented** values for `MAKE_WEBHOOK_SECRET` and `MAILGUN_WEBHOOK_SIGNING_KEY` — any strings; real ones arrive in Phase 8. Curl uses these same values to authenticate/sign.
6. **`src/lib/supabase.ts`** — export `supabaseAdmin` (server) / `supabaseClient` (anon). Every DB call needs the client. Admin usage stays in server files (routes/services); the secret never reaches the browser because it lacks the `NEXT_PUBLIC_` prefix. Depends on env vars from step 5.
7. **Extend `src/lib/types.ts`** — add `Post`, `IngestPayload`, `EmailPayload`, `IngestResult`. TypeScript blocks downstream files until these exist.
8. **`src/lib/db/trucks.ts` + `src/lib/db/posts.ts`** — `getActiveTruckById()`, `insertPost()`. The service needs its DB primitives. Depends on client + types.
9. **`src/lib/validators/ingest.ts` + `email.ts`** — payload validation + HMAC/recipient parsing. HMAC uses `crypto.timingSafeEqual` (constant-time), not `!==`. Pure functions; may run in parallel with step 8, but must precede the service/routes.
10. **Install Vitest + write `vitest.config.ts` + `email.test.ts`** — `npm i -D vitest`, add `test` scripts, config with Node env and a **manual** `resolve.alias` mapping `@` → `./src` (avoids the `vite-tsconfig-paths` dependency). Cover `verifyMailgunSignature` (valid passes / tampered fails) and `extractTruckIdFromRecipient` (valid + malformed). Depends on step 9. Run `npm run test:run` → green.
11. **`src/lib/services/ingestion.ts`** — synchronous `prepareWebhookIngest()` / `prepareEmailIngest()` (validate → verify truck active → build row → return `IngestResult`) and deferred `persistPost(row)` (raw insert, catches `23505`). Sets `posted_at` per lane (webhook → ingest time; email → Mailgun `timestamp`). Depends on steps 7–9.
12. **`src/app/api/ingest/route.ts`** — export `runtime = 'nodejs'`. **Synchronously**: check `X-Make-Secret` (constant-time) → validate payload → `prepareWebhookIngest()`; map any failure to 401/400. On success, return **200**, then `after(() => persistPost(row))` (`after` imported from `next/server`). Depends on service.
13. **`src/app/api/email/route.ts`** — same shape for the email lane, but parse the body with **`await request.formData()`** (Mailgun posts `multipart/form-data`, not JSON) and convert to a plain object first. Then synchronous HMAC verify + `prepareEmailIngest()` (can 400), then 200, then `after(() => persistPost(row))` (`runtime = 'nodejs'`). Depends on service.
14. **Verify with curl** — with the local stack running, use **`curl.exe`** in PowerShell (plain `curl` aliases to `Invoke-WebRequest` with incompatible flags; plain `curl` is fine only in Git Bash). For the **webhook** lane, send the dev `MAKE_WEBHOOK_SECRET` in the `X-Make-Secret` header. For the **email** lane's valid-HMAC happy path, generate the signed **form-encoded** request with `scripts/sign-mailgun.mjs` (Mailgun uses `multipart/form-data`, and a valid signature can't be hand-typed). Hit each endpoint: valid post (→200), wrong secret (401), bad payload (400), unknown/inactive truck (400), duplicate `instagram_post_id` (still 200, **no** second row — discard happens in `after()`, so 409 is never returned in this phase); confirm `posts` row lands with `parsing_status='pending'` (inspect via Studio).

Order rationale: **tooling → schema → client → types → db → validators → tests → service → routes → verify.** Toolchain first because the local DB is a hard dependency of every later step; then each code layer depends only on those above it (routes → services → db; validators pure), so every file compiles the moment it's written with no forward references.

## Rationale

- **Synchronous validation before the 200, raw write in `after()`** — CLAUDE.md requires 400/401 for bad secret, bad payload, and unknown/inactive truck (impossible once 200 is sent) *and* requires webhooks to return 200 immediately with DB work deferred to `after()`. Validating synchronously and deferring only the raw-post write is the only split honoring both rules.
- **`getActiveTruckById` in the DB layer, active-check in the service** — routes stay HTTP-only; the DB layer exposes the query, the service decides what a null result means. Keeps layers clean.
- **`ingestion.ts` created thin now, grows in Phase 3** — the routes need a service to call; creating it now with stable signatures (`prepare*Ingest` synchronous + `persistPost` deferred) means Phase 3 adds parser/override logic *inside* `persistPost` (after the raw insert) without touching the routes.
- **Full schema migration in Phase 2, not incremental** — one authoritative `0001_initial_schema.sql` matching the documented schema avoids migration churn and lets `supabase start` reflect the real DB from day one. Tables unused this phase still exist.
- **RLS authored in the migration** even though all Phase 2 writes use `supabaseAdmin` — RLS-off tables are an easy-to-forget security footgun; authoring policies alongside the tables is cheaper than retrofitting, and `service_role` bypasses them so nothing breaks.
- **HMAC verification in the validator layer, constant-time** — it's pure input validation (no HTTP, no DB), so it belongs with the other validators and stays unit-testable. The signature check (and the `X-Make-Secret` check) use `crypto.timingSafeEqual` with a length guard, not `!==` — the context's `!==` example is illustrative, not the final implementation.
- **Vitest pulled forward for the two pure security functions** — signature verification and recipient parsing are the only security boundary in this phase and are pure/zero-infra, so unit-testing them now (rather than waiting for Phase 3's Vitest setup) closes a real gap cheaply. Route handlers and the ingestion *integration* tests remain Phase 3 / curl.
- **`posted_at` set per lane** — webhook payloads carry no timestamp, so `posted_at` = ingest time (`now()`); email uses the Mailgun `timestamp` (already parsed for HMAC), converted from Unix seconds, falling back to ingest time if absent. Honest provenance without inventing data.
- **`raw_json` stores the entire incoming payload** — per "Raw post always stored BEFORE parsing — never lose incoming data." The `posts` table is the future ML corpus, so we persist the complete request body, not just extracted fields.
- **`runtime = 'nodejs'` on both routes** — the handlers use `after()`, Node `crypto` (HMAC), and `supabaseAdmin`, none of which are Edge-safe. CLAUDE.md mandates the Node runtime for Supabase and states `after()` is Node-only. Setting it explicitly (rather than relying on the default) documents the hard requirement and prevents an accidental Edge opt-in.
- **`after()` imported from `next/server`, raw insert first** — `unstable_after` does not exist in Next.js 16. Inside `after()` the raw `posts` insert must be the **first** operation so "raw stored before parsing" still holds when Phase 3 adds parsing after it. Accepted risk: if the `after()` write fails after the 200 has been sent, Make.com will not retry and that row is lost — logged, not guarded against in Phase 2, consistent with the "return 200 immediately" rule.
- **No `server-only` guard in Phase 2 — the env boundary is the real protection.** Next.js only inlines `NEXT_PUBLIC_`-prefixed vars into the client bundle, so `SUPABASE_SERVICE_ROLE_KEY` (unprefixed) is `undefined` in the browser and the secret cannot leak regardless of imports. In Phase 2 no client code imports Supabase at all (map still on fake data; `supabaseClient` unused until Phase 4), so the accidental-import scenario can't occur. The `import 'server-only'` build-time guard is deferred to **Phase 4**, when client hooks first import the anon client and that risk becomes real — adding the dependency now would guard against nothing.
- **`instagram_post_id` uniqueness enforced by the DB in Phase 2** — the `posts_instagram_post_id_unique` partial index ships in the migration, so a duplicate real ID raises a Postgres `23505` on insert even before Phase 3's dedup logic exists. The service catches `23505` and discards gracefully; the caption+60s crosspost check is the part deferred to Phase 3.
- **`409` is not returned in Phase 2** — CLAUDE.md's error format lists `409` for a discarded duplicate, but because the raw insert (and its `23505` catch) runs inside `after()` *after* the 200 is sent, a duplicate always resolves as **200 + silent discard**. This is consistent with "return 200 immediately," not a contradiction; `409` becomes relevant only if a synchronous pre-response dedup is ever added (not planned).
- **`Post.source` is a six-value union** (`instagram | facebook | tiktok | email | manual | webhook`) per the `posts.source` column — distinct from `Location.source` (three values). Do not reuse the `Location` source type for posts.
- **`posted_at` for email uses the Mailgun signature `timestamp`** (≈ when Mailgun relayed the message), a deliberate proxy for raw storage — not the original email `Date` header, which isn't needed until/if the parser uses it.

## Acceptance Criteria

**Tooling**
- `wsl --status`, `docker ps`, and `npx supabase --version` all succeed on the dev machine.
- Docker Desktop is running and `npx supabase start` brings the local stack up with no errors; Studio is reachable at its local URL.
- `npm run test:run` executes Vitest and the `email.test.ts` suite passes (valid signature accepted, tampered signature/token rejected, malformed recipient → null, valid recipient → uuid).

**Schema & seed**
- `npx supabase start` runs the migration with no errors; all five tables (`trucks`, `posts`, `locations`, `geocoding_cache`, `users`) exist with the documented columns, indexes, and RLS enabled.
- `seed.sql` inserts at least 2 active trucks and 1 inactive truck; their `truck_id`s are retrievable for curl.

**Webhook lane (`POST /api/ingest`)**
- Valid payload + correct `X-Make-Secret` + active `truck_id` → **200**, and a `posts` row is created with `source` set, `parsing_status='pending'`, `posted_at` = ingest time, and the full body in `raw_json`.
- Missing/wrong `X-Make-Secret` → **401**, no `posts` row.
- Malformed payload (missing `truck_id`/`caption`, bad `source_platform`) → **400**, no `posts` row.
- Unknown or inactive `truck_id` → **400**, no `posts` row.
- The `X-Make-Secret` comparison is constant-time (`crypto.timingSafeEqual`).
- The route exports `runtime = 'nodejs'` and imports `after` from `next/server`; the `posts` row appears shortly after the 200 (written in `after()`, not on the request path).
- Re-POSTing a payload with an already-stored `instagram_post_id` does **not** create a second row and does **not** surface an unhandled error — the service catches the `23505` unique-violation and discards.

**Email lane (`POST /api/email`)**
- Valid Mailgun payload + valid HMAC + active truck (from `recipient`) → **200**, `posts` row created with `source='email'`, `parsing_status='pending'`, `posted_at` derived from the Mailgun `timestamp`, full `raw_json`.
- Invalid HMAC signature → **400**, no `posts` row. The signature comparison is constant-time (`crypto.timingSafeEqual`).
- `recipient` not matching `{uuid}@in.yourapp.se` → **400**, no `posts` row.
- Valid format but unknown/inactive truck → **400**, no `posts` row.

**Cross-cutting**
- All error responses are `{ "error": "message" }` with the correct status; no stack traces leaked.
- `supabaseAdmin` used only in server code (routes/services); `NEXT_PUBLIC_` never prefixes a secret key, so the service-role key is never present in any client bundle.
- Both routes export `runtime = 'nodejs'`.
- `tsc --noEmit` passes; no parser, geocoding, or `locations` writes occur anywhere in this phase.

## Open Decisions

1. **Email domain** — `{truck_id}@in.yourapp.se` is a placeholder; the real inbound domain (and whether it's env-configurable vs. hardcoded in the validator) is TBD. **Must be resolved before step 9** — `extractTruckIdFromRecipient`'s reject case and `email.test.ts`'s fixtures both depend on the exact domain.
2. **Validation approach — hand-rolled vs. Zod** — plan assumes hand-written type guards returning `null`; Zod isn't a dependency yet. Decide at implementation whether to add it or stay dependency-free.
3. **`IngestResult` failure granularity** — how many distinct failure reasons the service returns and how the route maps each to a status code. Finalized when writing the service.
4. **Supabase environment — RESOLVED: local via Docker now, hosted in Phase 5.** Install Docker Desktop + the Supabase CLI as a devDependency (`npm i -D supabase`, run via `npx supabase`) and run the local stack for all Phase 2 dev/test (steps 1–5). A hosted project is added in Phase 5 (first deploy) using the same migration files via `npx supabase db push`. CLI install channel decided: **devDep + `npx`** (not scoop/global — pins the version in the repo).
5. **`users` table + `auth.users` FK** — under `npx supabase start` the `auth` schema exists, so the FK to `auth.users` applies cleanly (it would only fail under a bare `psql` run without the `auth` schema). The FK itself is not a blocker; the only real choice is whether to author the `users` table now (harmless, unused until Phase 5 auth) or defer it to Phase 5. Lean: include it now for one authoritative schema.
6. **Seed truck UUIDs — fixed vs. random** — fixed UUIDs make curl commands copy-pasteable and repeatable across `db reset`; lean fixed, confirmed when writing `seed.sql`.
7. **`source` value for webhook posts** — store the specific platform (`instagram`/`facebook`/`tiktok`) or the generic `webhook`? Decide when building the service.
