# Process log — misses and what they say about the process

A record of defects, wrong turns, and stale guidance **for the purpose of fixing the
development process**, not for blame or for tracking bugs. Bugs live in GitHub
issues. This file exists to answer questions like:

- Which gate actually catches things — and which ones are decorative?
- Which documents keep going stale, and why?
- Are fixes creating new defects (overcorrection)?
- Which CLAUDE.md rules turned out to be wrong or harmful?

**Append-only.** Never rewrite history here: rows, retrospectives and the dated
decision sections all stay as written, and a miss that later turned out to be a
non-issue gets a follow-up row, not a deletion. A dated section may gain a pointer
note, in italics with its issue number, when what it describes has moved; its own
text stays. The one exception, approved by the owner: the detail entries that used
to follow the table were removed on 2026-10-17 (IS #152), and are kept unchanged on
the `archive/process-log-details` tag.

<details>
<summary>For the record: how the negation would have worked, had we wanted it</summary>

`.claude/` excludes the **directory**, and git does not descend into an excluded
directory, so a later `!.claude/process-log.md` is never evaluated — verified, it
stays ignored. Excluding the contents instead (`.claude/*`) leaves the negation able
to take effect. Also note `.gitignore` has **no trailing newline**, so appending
without a leading `\n` silently concatenates onto the `.claude/` line and corrupts
the pattern. Both facts cost three attempts to establish (see entry #11).

</details>

## How to use it

**Write an entry when:** something got through a gate it should not have; a
document or rule turned out to be wrong; a fix introduced a new defect; or the same
class of thing is caught twice.

**Do not write an entry for:** ordinary bugs found and fixed while writing the code.
That is just work. The bar is *"this says something about the process."*

**A miss whose story doesn't fit a row:** write the story in the body of the PR the
row rides in, and keep the row to the summary. Every new row lands through a PR (CLAUDE.md,
"Doc changes"), so a row whose `Where` is `n/a` still has one. (The detail entries
that used to hold such stories were removed; see "Append-only" above.)

**Read it at the end of every milestone: the milestone retrospective.** A log nobody
reads is a diary. As a one-line rule it was skipped at the end of Phase 2, and Phase
3's only happened as a planned issue (#128), so every milestone plan now includes it
(#146). This is the only copy of the procedure, including its order and blocking
rules; the commands and CLAUDE.md only point here. (The Phase 3 retrospective opens by
quoting the one-line rule this replaced.)

1. **Range.** From the first row after the previous retrospective's range to the last
   row written before this retrospective starts. State both numbers. The previous
   retrospective is the last section headed `## Phase <N> retrospective (…)`. Rows
   written later, by this retrospective and its follow-ups, belong to the next range.
2. **Counts.** Record, in a section after the previous retrospective, headed
   `## Phase <N> retrospective (<date>, #<issue>)`, e.g.
   `## Phase 4 retrospective (2026-10-17, #148)` (a milestone without a phase number
   uses its name in place of `Phase <N>`), the output of
   `bash scripts/process-log.sh tally 9 <first> <last>` (Cause) and
   `bash scripts/process-log.sh tally 7 <first> <last>` (Caught by: rows from the
   values block's `caught-by-from-row` start with a group, which `tally 7` counts;
   earlier rows are free text, grouped by hand as the Phase 3 retrospective does), with
   those commands.
3. **The previous retrospective's actions.** For each, did the misses it targeted
   drop? Keep, adjust or retire it, citing the rows as evidence. A rule that stopped
   nothing is a cost, not a safeguard.
4. **At most two new actions,** each a mechanism (a check, a template field, a
   script), never just advice. Aim them where misses could have been caught earlier,
   not just at the biggest number: code review is usually the biggest `Caught by`
   because that is where misses surface. Zero new actions is a valid answer.
5. **Follow-up issues.** Every change the retrospective decides (a new action, or
   adjusting or retiring an old one) becomes an issue: written in the `/create-issues`
   issue format, checked against its Step 5 list (Failure modes included: an action is
   a mechanism, so usually a guard), and created through its Steps 6–7 (pre-flight
   checks, `--body-file`). Its Steps 1–4 don't apply: there is no plan to break down.
   One issue may carry several small changes, as #142 carried #128's.
6. **Order, blocking and closing.** A plan's closing steps are this retrospective and
   then the reconciliation of `project-context.md` (the end-of-phase task CLAUDE.md
   describes); `/create-milestone` and `/create-issues` add both. The retrospective
   issue is **blocked by every other planned issue**, so its range is complete. The
   reconciliation issue is **blocked by the retrospective, and by each follow-up as it
   is opened** (add it to the reconciliation's `Blocked by`), so the context records
   the changed process. **The reconciliation also carries forward each numbered
   decision that outlives the phase** (a process, tooling or standing rule): the
   plan's own, and any added to an earlier plan after that plan's reconciliation
   merged (Phase 4's #14 is the first). Each goes into `project-context.md`, or into
   CLAUDE.md when it is a rule, citing the plan decision. Without that, the next plan
   replaces it as "the current plan" and the decision stops being read. The milestone
   closes once the reconciliation merges.
7. **An already-closed milestone** (Phase 4's case when this was added): create the
   retrospective issue and its follow-ups the way part 5 creates follow-ups, with no
   milestone (skip Step 6's milestone check), and finish them before the next plan is
   written. The next plan's reconciliation picks up their changes.

### Columns

**What one row is.** A review round is one row: "found N, M applied" (N counts every
item the round raised, applied or not), the round's headline `Cause`, and the other
findings under "Also". Any other miss is one row, including one found while working
that a later round also touches (rows 289, 296). This is the practice since row 268;
rows 268 and 270 predate the counting rule, and the Phase 4 retrospective counts them as
8 and 9. Most Phase 3 review rows recorded one finding each, so tallies across that
boundary don't compare (row 308).

**`Where`** — exactly one of these three forms, no variants:

```
PR #74 / IS #55     a miss that happened in that work
→ IS #64            a miss found before any PR existed; the issue is where the fix lands
n/a                 a workflow or behavioural miss with nothing to point at
```

**Both numbers carry a prefix — `PR #` and `IS #`.** Write `PR #74 / IS #55`, never
`74 / IS #55`. The prefixes are what stop a PR and an issue being read as each other
at a glance, and both are needed for that: a bare leading number is exactly the
ambiguity the `IS` prefix exists to remove. Multiple issues share one prefix:
`→ IS #64, #68`.

*(This paragraph replaced one that gave the format correctly and then said "the PR
number needs no prefix", meaning it needs no `IS` prefix. Twenty-seven rows were
written as `74 / IS #55` before a reader caught it — see row 55.)*

Use `n/a` when a miss genuinely has no PR, rather than forcing a reference.

**A leading `→` means "fixed in", not "occurred in".** A miss found during *planning*
happened before any issue existed, so it has no origin reference — but once the fix is
scheduled, the issue that carries it is where the claim becomes checkable. `IS #53`
means the miss happened in that work; `→ IS #64` means the correction lands there.
Same durability purpose, opposite direction, so the notation distinguishes them.
Added 2026-08-22, retroactively, for the eight planning-phase rows that had one.

**Some `n/a` rows are correct and must stay that way.** Rows 11, 12, 14, 17, 21–24 are
behavioural (something was claimed, assumed, or not done) or concern the plan document
itself (which was gitignored at the time, so it had no PR). There is nothing to point at, and inventing a reference would be
worse than the gap. Do not "fix" these.

The issue carries the intent, the PR carries the change — together they answer both
"what were we trying to do" and "what did we actually do". **The PR and issue hold
the diff and the review discussion, which this log only summarises.** A row without
a reference has no evidence behind it. (Until IS #116 this was also the durability
hedge, because the log was untracked and lived on one machine. It is tracked now,
but the evidence argument still holds.)

**`Artifact`** — *the dev-process file that was wrong, missing, or not followed.*
Not "the file that got edited". Use `code-only` when no process artifact is
implicated. A doc appears here both when it was **wrong** (#1) and when it was
**correct but not consulted** (#7) — the `Cause` column disambiguates, and both are
worth counting, because "this rule keeps being ignored" is as actionable as "this
rule is stale".

Values: the values block's `artifact` line (end of this section). `docs` means several
docs at once; `code-only` means no process artifact is implicated.

**`Escaped`** — how far it travelled before being caught, the real cost signal.
Values: the values block's `escaped` line, nearest first.

**`Caught by`** — what found the miss. The cell starts with one backticked group,
then free text: `` `code-review` r2 (user-requested) ``, `` `self` counting for #148 ``.
Required from the row on the values block's `caught-by-from-row` line, and `check`
enforces it; the groups are its `caught-by` line. Earlier rows stay as written and
are grouped by hand: rows 308–314 are the first
range that needs it (the Phase 5 retrospective). The groups follow the Phase 3
retrospective's rule, as its Phase 4 count applied it. **A review is grouped by what was
reviewed**, whoever asked for it (`code-review`, `plan-review`). **Anything else is
grouped by who found it**: `self` while doing the work, `user` the owner. So the
owner's browser check (row 282) is `user`, and the end-of-phase check run while working
(row 303) is `self`. If two found it, the group is the one that found it first, and the
other goes in the text. Older free-text rows name that one first (rows 289, 296).

- **code-review:** a review of code or a PR (`/code-review` rounds), whoever asked for
  it. Put the round in the text (`r2`).
- **plan-review:** a review of a plan, an issue, the context or a design doc, whoever
  asked for it (rows 266–267).
- **self:** found while doing the work: writing, running, probing, mutation testing,
  re-reading output, or a check run as part of it (the gates, the end-of-phase check of
  row 303).
- **user:** found by the owner outside a review: noticing, asking, pushing back, or a
  check the owner runs, such as a browser check (row 282).

**The values block.** `scripts/process-log.sh` checks rows against the values in this
block, and only these; the prose above explains them. Change a value here and nowhere
else. `artifact-drift-rows` are exempt from the `artifact` list (known drift, row
297). From `cap-from-row`, a row's Miss is at most `cap-miss` characters and its Fix
at most `cap-fix`: the details go in the PR body. Earlier rows are exempt (IS #155).
The Cause names in the taxonomy below must match the `cause` line, and `check` says so
when they don't.

```values
artifact: CLAUDE.md project-context README process-log command plan issue process docs code-only
escaped: pre-commit pre-merge merged crossed-phase production n/a
cause: stale-doc missing-gate gate-skipped unverified-assumption incomplete-guard overcorrection imprecise-claim manual-drift
caught-by: code-review plan-review self user
caught-by-from-row: 315
artifact-drift-rows: 197-267
cap-from-row: 321
cap-miss: 600
cap-fix: 300
```

### Cause taxonomy

Keep to these; add a value only when something genuinely does not fit, here and on the
values block's `cause` line.

| Cause | Meaning |
|---|---|
| `stale-doc` | A project rule/doc was wrong, and following it caused the defect |
| `missing-gate` | No check existed that would have caught it |
| `gate-skipped` | A check existed but was not run |
| `unverified-assumption` | Acted on something believed but never confirmed |
| `incomplete-guard` | A guard covered some failure modes but not all of them |
| `overcorrection` | A fix for a previous miss introduced a new defect |
| `imprecise-claim` | A comment/doc asserted more than was actually true |
| `manual-drift` | Hand-maintained data (counts, lists, status) fell out of sync |

**`next build` is a load-bearing gate that was not in the loop.** Entry #1 passed

**The largest cause group is `incomplete-guard`, and it clusters on one function.** #2, #3, #4
and #6 are four separate failure modes of one small piece of numeric/string input
handling, each found only after the previous fix. The lesson is not "be more
careful" — it is that when guarding parsed input, the failure modes should be
*enumerated up front* (empty, non-numeric, overflow, underflow, storage-range,
ambiguous-encoding), not discovered one review at a time.

**One entry is an overcorrection, and it is the most expensive one.** #7 was a fix
for #6 that broke a rule written in the same PR. Its lesson generalises: reaching
for input validation when a structural invariant already covers the case adds cost
without adding safety. Structural invariants do not reject valid input; validation
does.

**`unverified-assumption` ties for largest, and every instance was cheap to check.**
#5 (a confident migration comment), #9 (assuming GitHub parses `Closes … in #45`),
#11 (this file's own gitignore advice) and #12 (assuming the dev docs *should* be
tracked) each took minutes to verify or one question to ask, and each would have
shipped wrong. The pattern is not carelessness — it is stating a
mechanism confidently *without* running it. #11 is the useful one to remember: the
first two attempts to test it were themselves flawed (a missing trailing newline
corrupted the pattern; then a stderr warning was misread as success), so the answer
only emerged on the third attempt. Verifying is not free, but it is cheaper than
the alternative in every case here.

**One PR produced the largest share of all misses.** `tally 4` puts PR #54 well
ahead of everything else. That PR started as a small contract change and accreted a
replay guard, a signature redaction, a migration and a security fix across four
review rounds. The correlation worth watching is scope growth against miss count —
if the next big PR repeats it, the lesson is to split rather than to review harder.

**Most misses implicate a dev-process artifact, not just code.** `tally 5` shows
`code-only` is a minority: the rest point at `CLAUDE.md`, `README`, `process`, this
log itself, or several docs at once. `CLAUDE.md` appears twice for opposite reasons
— once **wrong** (#1) and once **correct but not consulted** (#7). Those need
different fixes: the first is a maintenance problem, the second a workflow one.
This split is the main thing the file was built to expose, and it showed up in the
first session.

**Not every miss is a defect — #12 is a process miss.** Repeatedly proposing a fix
for something that was a deliberate choice costs attention and erodes trust in the
suggestions that do matter. The fix is structural: record decisions with their
rationale where the next session will read them, so a settled question stays
